CUTIE COLLECTION
FULL-STACK E-COMMERCE APPLICATION
PROJECT REQUIREMENTS AND SETUP DOCUMENT

======================================================================
1. PROJECT OVERVIEW
======================================================================

Project Name: Cutie Collection
Project Type: Full-stack e-commerce web application

Purpose:
Cutie Collection allows customers to register, log in, browse products,
search and sort products, manage a cart and wishlist, place orders, make
payments, and view order history. Administrators can manage categories,
products, stock, and customer orders.

3. USER ROLES
======================================================================

CUSTOMER:
- Register and log in
- View, search, sort, and paginate products
- Manage cart and wishlist
- Manage shipping addresses
- Place orders and make payments
- View and cancel eligible personal orders

ADMIN:
- Manage categories
- Manage products and stock
- View all orders
- Update order status
- Access the admin dashboard

All administrator operations must use role-based authorization.

4. AUTHENTICATION AND AUTHORIZATION
======================================================================

POST /api/auth/signup
POST /api/auth/login
GET  /api/users/me

Signup request example:
{
  "name": "Rashi",
  "email": "rashi@example.com",
  "password": "Password@123"
}

Login request example:
{
  "email": "rashi@example.com",
  "password": "Password@123"
}

Protected request header:
Authorization: Bearer <jwt-access-token>

Requirements:
- Hash passwords with BCrypt
- Prevent duplicate email registration
- Generate expiring JWT access tokens
- Return HTTP 401 for missing, invalid, or expired authentication
- Return HTTP 403 when the authenticated user lacks permission
- Never return passwords or password hashes through APIs
- Load the JWT secret from an environment variable

5. CATEGORY MANAGEMENT
======================================================================

Public endpoints:
GET /api/categories
GET /api/categories/{categoryId}

Administrator endpoints:
POST   /api/admin/categories
PUT    /api/admin/categories/{categoryId}
DELETE /api/admin/categories/{categoryId}

Category fields:
- id
- name
- description
- active
- createdAt
- updatedAt

Validation:
- Name is required and unique
- Blank names are not allowed
- Categories associated with products should be deactivated rather than
  permanently deleted

======================================================================
6. PRODUCT MANAGEMENT
======================================================================

Public endpoints:
GET /api/products
GET /api/products/{productId}
GET /api/products/category/{categoryId}
GET /api/products/search?keyword={keyword}
GET /api/products/paged?page=0&size=12&sortBy=price&direction=asc

Administrator endpoints:
POST   /api/admin/products
PUT    /api/admin/products/{productId}
DELETE /api/admin/products/{productId}

Product fields:
- id
- name
- description
- price
- stockQuantity
- imageUrl
- active
- categoryId
- categoryName
- createdAt
- updatedAt

Validation:
- Name is required
- Price must be greater than zero
- Stock quantity cannot be negative
- Category must exist
- Inactive products must not appear in normal customer results
- Allowed sorting fields: name, price, stockQuantity, createdAt
- Allowed directions: asc, desc

======================================================================
7. CART MANAGEMENT
======================================================================

POST   /api/cart/items
GET    /api/cart
PUT    /api/cart/items/{productId}
DELETE /api/cart/items/{productId}
DELETE /api/cart

Add-item request:
{
  "productId": 1,
  "quantity": 2
}

Update-quantity request:
{
  "quantity": 3
}

Requirements:
- Each customer has a personal cart
- Quantity must be at least one
- The backend validates available stock
- The backend reads the current price from the database
- The backend calculates line totals and the grand total
- A customer cannot access another customer's cart

======================================================================
8. WISHLIST MANAGEMENT
======================================================================

POST   /api/wishlist/{productId}
GET    /api/wishlist
DELETE /api/wishlist/{productId}
DELETE /api/wishlist

Requirements:
- A product cannot be duplicated in the same wishlist
- A customer cannot access another customer's wishlist

POST   /api/addresses

======================================================================
10. ORDER MANAGEMENT
======================================================================

Customer endpoints:
POST  /api/orders
GET   /api/orders/my
GET   /api/orders/{orderId}
PATCH /api/orders/{orderId}/cancel

Administrator endpoints:
GET   /api/admin/orders
GET   /api/admin/orders/{orderId}
PATCH /api/admin/orders/{orderId}/status

Order statuses:
- PENDING
- CONFIRMED
- PROCESSING
- SHIPPED
- DELIVERED
- CANCELLED

Payment statuses:
- PENDING
- CREATED
- PAID
- FAILED
- REFUNDED

Requirements:
- Do not allow an order from an empty cart
- Validate stock before creating an order
- Save product price in the order item at order time
- Save a snapshot of the shipping address
- Calculate totals on the backend
- Update stock within a database transaction
- Clear the cart after successful order placement
- Customers may access only their own orders
- Shipped or delivered orders cannot be cancelled by customers

======================================================================
11. RAZORPAY PAYMENT MANAGEMENT
======================================================================

POST /api/payments/create-order
POST /api/payments/verify

Create-payment request:
{
  "orderId": 1
}

Verification request:
{
  "applicationOrderId": 1,
  "razorpayOrderId": "<razorpay-order-id>",
  "razorpayPaymentId": "<razorpay-payment-id>",
  "razorpaySignature": "<razorpay-signature>"
}

Requirements:
- Create the Razorpay order from the backend
- Calculate the amount from backend order data
- Never accept the final payment amount from the frontend
- Never send the Razorpay secret key to the frontend
- Verify the Razorpay signature on the backend
- Mark the application order as paid only after successful verification
- Handle duplicate callbacks safely
- Keep test and production keys separate

14. STANDARD ERROR RESPONSE
======================================================================

Example:
{
  "timestamp": "2026-08-11T10:30:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Price must be greater than zero",
  "path": "/api/admin/products",
  "validationErrors": {
    "price": "Price must be greater than zero"
  }
}

Recommended HTTP statuses:
- 200 OK
- 201 Created
- 204 No Content
- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 409 Conflict
- 500 Internal Server Error

Do not expose stack traces or internal exception details to customers.

16. ENVIRONMENT VARIABLES
======================================================================

Backend variables:
DB_URL=<postgresql-jdbc-url>
DB_USERNAME=<database-username>
DB_PASSWORD=<database-password>
JWT_SECRET=<strong-random-jwt-secret>
JWT_EXPIRATION_MS=3600000

RAZORPAY_KEY_SECRET=<razorpay-secret>
FRONTEND_URL=http://localhost:5173

Frontend variable:
VITE_API_BASE_URL=http://localhost:8080

Rules:
- Keep real values only in local environment variables and deployment
  platform settings
- Commit .env.example with placeholder values only
- Do not commit .env
- Do not place backend secrets in frontend variables
- Spring Boot generally uses a JDBC URL such as:
  jdbc:postgresql://<host>:5432/<database>?sslmode=require

17. LOCAL SETUP
======================================================================

1. Create local files from the safe templates:

Backend:
- Copy .env.example to .env only if the chosen local setup loads .env
- Otherwise configure the listed variables in the terminal or IDE

Frontend:
- Create .env.local inside cutie-collection-frontend
- Add VITE_API_BASE_URL=http://localhost:8080

2. Start backend:

cd cutie-collection-backend
mvn clean test
mvn spring-boot:run

3. Start frontend:

cd cutie-collection-frontend
npm install
npm run dev

Local URLs:
- Frontend: http://localhost:5173
- Backend: http://localhost:8080
- Swagger: http://localhost:8080/swagger-ui/index.html

======================================================================
18. DEPLOYMENT
======================================================================

Architecture:
React -> Vercel -> Spring Boot REST API -> Render -> Neon PostgreSQL

Vercel:
- Set the frontend root directory
- Set the build command and output directory
- Add VITE_API_BASE_URL with the deployed backend URL
- Do not store backend secrets in Vercel

Render:
- Set the backend root directory
- Configure build and start commands
- Add backend environment variables from .env.example
- Set FRONTEND_URL to the deployed Vercel URL
- Configure a health-check endpoint

Neon:
- Store the JDBC connection data only in Render
- Require SSL
- Use schema migrations
- Never publish the connection password

======================================================================
20. SECURITY REQUIREMENTS
======================================================================

Never commit:
- .env files
- Database passwords or credential-bearing URLs
- JWT secrets
- Razorpay secrets
- Email passwords
- AWS access keys
- Personal identity documents
- Real customer or administrator passwords

Repository-safe files:
- .env.example with placeholder values
- application.properties using ${VARIABLE_NAME}
- README.md without secrets
- RequiredDoc.txt without secrets

Any credential previously committed to Git must be rotated. Removing it
from the latest file does not automatically remove it from Git history.
